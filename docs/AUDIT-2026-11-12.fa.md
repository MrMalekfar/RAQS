# حسابرسی RAQS و برنامهٔ رفع ایرادها

تاریخ: ۲۰۲۶-۱۱-۱۲ — مبنای کد: `521c032`، شاخهٔ `codex/profile-schema-migration`.

RAQS پاسخ حسگر اتمی ریدبرگ را از تنظیم میدان و حل معادلهٔ Lindblad تا استخراج IF و تخمین زاویهٔ ورود محاسبه می‌کند. مسیرهای CLI، مطالعهٔ چندنقطه‌ای و میزکار Qt، مصرف‌کنندگان این هسته‌اند. بار کاری مبنای این بررسی، استفادهٔ پژوهشی محلی با یک کاربر، چند پردازهٔ محاسباتی و تکرارهای Monte Carlo است؛ میزبانی عمومی و چندکاربره در دامنهٔ محصول فرض نشده است.

**نتیجه:** حفاظت‌های فیزیکی و آزمون‌های هدفمند پروژه قابل‌توجه‌اند، اما سلامت همهٔ ترکیب‌های تنظیمات قابل تأیید نیست. پیش از اتکا به خروجی‌های پژوهشی، سه ایراد ذخیره‌سازی/اعتبارسنجی زیر باید رفع شوند. سه موضوع دیگر نیز در مقداردهی و قابلیت بازتولید نیاز به اصلاح دارند. هیچ کد اجرایی، baseline، seed یا tolerance در این حسابرسی تغییر نکرده است.

## روش و دامنهٔ واقعی بررسی

وضعیت Git پیش از بررسی ثبت شد. تغییر موجود `examples/README.md` و پوشه‌ها و فایل‌های ثبت‌نشدهٔ کاربر در `examples/` حفظ شدند. یافته‌ها به source فعلی مربوط‌اند؛ مثال‌های ثبت‌نشده، نسخهٔ انتشار مصوب فرض نشده‌اند.

برای نقشهٔ ساختار و مسیر فراخوانی از ابزار Codebase Memory استفاده شد. مهارت محلی هم‌نام در مسیرهای جست‌وجوشده پیدا نشد. ابزار برای پنج مسیر استنادی وضعیت `metadata_changed` داد؛ بنابراین نتیجهٔ گراف صرفاً راهنمای جست‌وجو بود و شواهد از فایل فعلی خوانده شد. مهارت `ponytail-audit` مبنای اولویت‌بندی و الزام سناریوی مشخص برای هر ایراد بود.

این حسابرسی، بررسی عمیق مسیرهای پرخطر است، نه ادعای خواندن تک‌تک خطوط مخزن. README، وابستگی‌ها، تنظیم pytest، CLI، parser، مقداردهی ARC، اجرای پروفایل/مطالعه، ذخیرهٔ آرایه‌ها، ساخت Hamiltonian، حل پایا و زمانی، استخراج IF، اتصال DoA، بخش‌هایی از نویز/آمار و چرخهٔ اجرای GUI بررسی شدند.

## ایرادهای ضروری

### ۱. گزارش جدید می‌تواند کنار آرایه‌های اجرای قبلی باقی بماند — P1

**محل:** `cli.py:275`، تابع `main`؛ `rydberg_aoa/simulation/profile_execution.py:353`، تابع `save_profile_results`.

**کار این بخش:** CLI ابتدا `run_report.json` را می‌نویسد و سپس آرایه‌ها را صادر می‌کند. بازنویسی پوشهٔ خروجی طبق README مجاز است.

**ایراد و شاهد:** اگر پوشه قبلاً آرایه داشته باشد و export جدید با خطای دیسک یا خطای یافتهٔ ۲ متوقف شود، گزارش جدید نوشته شده اما آرایهٔ قبلی باقی می‌ماند. در بازتولید با تزریق `OSError` به مرز ذخیره، دقیقاً «گزارش جدید + آرایهٔ قدیمی» مشاهده شد. این آزمون رفتار ذخیره را بررسی می‌کند و اجرای فیزیک مصنوعی را صحت علمی معرفی نمی‌کند. حتی بدون خطا، اجرای diagnostics در پوشهٔ sensing قدیمی، آرایهٔ قبلی را حذف یا بی‌اعتبار نمی‌کند.

**کمترین اصلاح کامل:** مسیر تک‌پروفایل نیز پوشهٔ اجرای تازه را الزام کند و پیش از محاسبه، مقصد متعارض را رد کند؛ اگر حفظ امکان بازنویسی لازم است، ابتدا کل اجرای جدید در پوشهٔ موقت نوشته و اعتبارسنجی شود و فقط پس از موفقیت منتشر شود. نشانگر تکمیل باید آخر نوشته شود. صرف جابه‌جاکردن ترتیب نوشتن دو فایل، تراکنش کامل نیست.

**معیار پذیرش:** در خطای ساخت NPZ، خطای نوشتن گزارش و diagnostics روی مسیر قدیمی، هیچ ترکیب قابل‌اشتباه از دو اجرا منتشر نشود؛ نتیجهٔ موفق قبلی دست‌نخورده بماند. CLI، مطالعه‌ها و مصرف‌کنندگان نتیجه باید قرارداد تکمیل یکسان و روشن داشته باشند.

**پیامد تعویق:** تحلیل یا نمودار بعدی ممکن است آرایهٔ یک اجرای دیگر را به تنظیمات گزارش تازه نسبت دهد.

### ۲. ذخیرهٔ IF-only با metadata معتبر طیف شکست می‌خورد — P1

**محل:** `rydberg_aoa/simulation/if_only.py:117`، تابع `save_if_only_arrays`؛ تولیدکننده در `rydberg_aoa/simulation/profile_spectrum.py`، تابع `run_profile_spectrum`.

**کار این بخش:** دادهٔ IF-only باید به‌صورت آرایه‌های عددی و بدون object/pickle ذخیره شود.

**ایراد و شاهد:** صادرکننده فقط `analytical_contract` را از دیکشنری طیف حذف می‌کند. نام `steady_state_backend` یک رشته و `radiative_model` یک دیکشنری است؛ هر دو به فهرست آرایه‌ها راه پیدا می‌کنند و شرط عددی‌بودن را می‌شکنند. دو حالت جداگانه بازتولید شد؛ کنترل همان خروجی بدون metadata موفق بود. parser نیز ترکیب `measurement.mode=if_only` با backend صریح و با مدل تابشی مثال `relax002` را پذیرفت. بنابراین موضوع صرفاً ورودی غیرمجاز نیست.

**کمترین اصلاح کامل:** قرارداد صریحی برای کلیدهای عددی طیف در هر دو صادرکنندهٔ AoA و IF-only برقرار شود؛ metadata در JSON گزارش بماند. اعتبارسنجی عددی حذف نشود و ذخیرهٔ object یا فعال‌کردن pickle راه‌حل نیست.

**معیار پذیرش:** export و بارگذاری با `allow_pickle=False` برای IF-only با backendهای `direct` و `qutip` و با radiative فعال موفق باشد؛ metadata در گزارش باقی بماند. آزمون فعلی export در `tests/test_noise013_if_only.py:157` این ترکیب را پوشش نمی‌دهد.

**پیامد تعویق:** حل معتبر و احتمالاً پرهزینه در آخرین مرحله شکست می‌خورد؛ در CLI با پوشهٔ تکراری، یافتهٔ ۱ نیز فعال می‌شود.

### ۳. API سازندهٔ مدل نرخ نامعتبر را بی‌صدا به حذف اتلاف تبدیل می‌کند — P1 در مصرف مستقیم API

**محل:** `rydberg_aoa/physics/hamiltonian/create_sensor_model.py:155`، `:181` و `:194`، تابع `create_sensor_model`؛ این تابع در `physics/__init__.py` صادر شده است.

**کار این بخش:** نرخ‌های decay، dephasing و transit را به collapse operator تبدیل می‌کند.

**ایراد و شاهد:** شرط `rate > 0` بدون کنترل قبلی، هم نرخ منفی و هم `NaN` را رد نمی‌کند؛ صرفاً operator مربوطه ساخته نمی‌شود. سه فراخوانی مستقل با decay منفی، dephasing برابر `NaN` و transit منفی، بدون خطا و با فهرست اتلاف خالی برگشتند. مثبت‌بودن ماتریس چگالی نمی‌تواند چنین تغییر اشتباه مدل را کشف کند.

**دامنه:** اعتبارسنجی پروفایل عمومی بسیاری از این ورودی‌ها را زودتر رد می‌کند. این یافته به API مستقیم و هر caller فاقد کنترل پیشین مربوط است؛ ادعا نمی‌شود JSON نامعتبر فعلاً از parser عمومی عبور می‌کند.

**کمترین اصلاح کامل:** در مرز عمومی تابع، طول و نوع بردارها و متناهی/نامنفی‌بودن نرخ‌ها بررسی شود؛ صفرِ معتبر حفظ شود. قرارداد `PreparedRadiativeGraph` و معنای فعلی `None` جدا و صریح بماند. در حلقه‌های داغ solver، هزینهٔ اعتبارسنجی باید اندازه‌گیری شود؛ هیچ نرخ یا کانالی خودکار تصحیح نشود.

**معیار پذیرش:** ورودی منفی، boolean، غیرمتناهی و طول نامعتبر خطای مشخص بدهد؛ صفر و حالت‌های معتبر، Hamiltonian و Liouvillian قبلی را بدون تغییر تولید کنند. callers در `steady_state.py` و `time_domain.py` و آزمون‌های parity/trace/Hermiticity/positivity بررسی شوند.

**پیامد تعویق:** استفادهٔ برنامه‌ای می‌تواند نتیجهٔ عددی ظاهراً سالم برای مدل فیزیکی ناخواسته تولید کند.

## اصلاح‌های بعدی

### ۴. import داخلی هنوز ARC و محاسبهٔ چگالی را فعال می‌کند — P2

**محل:** `rydberg_aoa/config/parameters.py:160` و `rydberg_aoa/config/atomic_config.py:33`؛ مسیر فراخوانی از `physics/__init__.py` و `arc/interface.py` نیز به آن می‌رسد.

**ایراد و شاهد:** `CALCULATED_N0 = calculate_atomic_density_with_arc()` در سطح ماژول اجرا می‌شود. import سازندهٔ Hamiltonian با ورودی کاملاً صریح، در محیط با پایگاه ARC فقط‌خواندنی، پیش از فراخوانی تابع با `sqlite3.OperationalError` شکست خورد. جمع‌آوری آزمون‌ها نیز از همین مسیر متوقف شد. جلوگیری از انتشار ترازهای حل‌شده، به معنی بی‌اثر بودن کل import نیست.

**اصلاح:** ساخت ARC و انتشار چگالی به مقداردهی صریح منتقل شود؛ خوانندگان پیش از مقداردهی خطای روشن بدهند. از مقدار پیش‌فرض ساختگی برای چگالی استفاده نشود. snapshot/rollback و مصرف‌کنندگان `CALCULATED_N0` و `SI_Constants.N0` همراه تغییر بررسی شوند.

**معیار پذیرش:** import ماژول‌های محاسباتی بدون ساخت atom و بدون نوشتن فایل موفق باشد؛ اجرای صریح با ARC خراب همچنان شکست بخورد. مسیر `--help` اکنون مستقل است و در این حسابرسی موفق بود؛ آن را خراب تلقی نمی‌کنیم.

**پیامد تعویق:** ابزارهای تحلیل ایستا و آزمون‌های مستقل از دادهٔ اتمی به وضعیت پوشهٔ ARC وابسته می‌مانند.

### ۵. زیرمجموعهٔ رگرسیون هنوز مرجع تاریخیِ نامعتبر را مطالبه می‌کند — P2

**محل:** `tests/test_physics_baseline_regression.py:19` و `tests/test_parameter_injection_rf002.py:35`؛ توضیح ناسازگاری در `post_physics_baseline.json:65`.

**ایراد و شاهد:** فایل post-physics صریحاً `phase0_baseline.json` را مرجع تاریخی نامعتبر برای فیزیک معرفی و تفاوت طول سلول، قرارداد Rabi، transit و واحدها را فهرست کرده است؛ بااین‌حال آزمون‌های فوق هنوز تطابق default فعلی با اعداد Phase 0 را مطالبه می‌کنند. مثال روشن، `od_factor=402643.6365` برای طول سلول قدیمی در برابر مقدار `301982.7274` ثبت‌شده برای ۷۵ میلی‌متر است. skip مجاز QN-001A این ناسازگاری مفهومی را رفع نمی‌کند.

**اصلاح:** فایل تاریخی دست‌نخورده بماند و آزمون سازگاری تاریخی از رگرسیون مدل جاری تفکیک شود. برای مدل جاری، fixture مستقل با prepared-channel صریح، منشأ، نسخهٔ کد/ARC، واحد و SHA-256 تولید و بررسی شود. `post_physics_baseline.json` نیز بدون بررسی علمی دوباره، مرجع خودکار جایگزین نشود؛ قدمت یا نام فایل تأیید اعتبار امروز نیست.

**معیار پذیرش:** رگرسیون جاری با کانال صریح واقعاً اجرا شود و نتیجهٔ skip را عبور مدل جاری نشان ندهد. baseline، tolerance یا seed صرفاً برای سبزکردن آزمون تغییر نکند؛ منشأ و hash مرجع قابل کنترل باشد.

**پیامد تعویق:** این زیرمجموعه نمی‌تواند شاهد روشنی برای حفاظت از قراردادهای فیزیکی فعلی باشد و پس از رفع مانع QN ممکن است بازگشت به فیزیک قدیمی را مطالبه کند.

### ۶. اجرای تک‌پروفایل CLI رسید کافی برای بازتولید ندارد — P2

**محل:** `cli.py:270` به بعد، در مقایسه با `raqs_gui/worker.py:68` به بعد.

**ایراد و شاهد:** CLI گزارش و آرایه را ذخیره می‌کند، اما snapshot کامل ورودی، hash فایل‌ها، شناسهٔ commit و نسخهٔ کامل کتابخانه‌های اصلی را مانند GUI ثبت نمی‌کند. گزارش اطلاعات فیزیکی متعددی دارد و نسخهٔ ARC را ثبت می‌کند، اما جای نسخهٔ دقیق کد و ورودی را نمی‌گیرد. پس از ویرایش پروفایل یا تغییر checkout، صرف دو فایل خروجی برای تشخیص نسخهٔ تولیدکننده کافی نیست. `InputProvenance` نیز برچسب منشأ علمی است، نه رسید نسخهٔ اجرا.

**اصلاح:** قرارداد موجود receipt در GUI به‌صورت حداقلی برای CLI نیز استفاده شود: snapshot ورودی مصرف‌شده، hash، commit/dirty state و نسخهٔ وابستگی‌های اصلی. این کار همراه یافتهٔ ۱ انجام شود تا دو قالب مستقل و ناسازگار ایجاد نشود؛ ذخیرهٔ snapshot باید به ورودی واقعاً مصرف‌شده متصل باشد.

**معیار پذیرش:** پس از تغییر فایل اصلی، پوشهٔ اجرا همچنان ورودی و نسخهٔ تولیدکنندهٔ خود را نشان دهد؛ دست‌کاری خروجی با بررسی hash تشخیص داده شود. نبود Git باید صریح ثبت شود، نه با مقدار ساختگی.

**پیامد تعویق:** مقایسهٔ نتایج بین نسخه‌ها و دفاع از منشأ محاسبات پژوهشی به حافظهٔ کاربر یا فایل‌های بیرون از پوشهٔ اجرا وابسته می‌ماند.
